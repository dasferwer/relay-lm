# Протоколы и учёт

## Какие API поддерживаются

OpenAI: `POST /v1/chat/completions`, текстовые `messages`, `max_completion_tokens`, `stream: true`, `stream_options.include_usage: true`. Адаптер читает текст из `choices[].delta.content`, итоговые токены из `usage` и ждёт `[DONE]`. Итоговый usage может не прийти при обрыве, поэтому завершение без него считается неуспехом. Основание: [OpenAI Chat API](https://developers.openai.com/api/reference/resources/chat).

Anthropic: `POST /v1/messages`, отдельное поле `system`, остальные сообщения и `max_tokens`. `message_start` задаёт входные токены, включая токены кеша; `message_delta.usage.output_tokens` заменяет предыдущее значение, поскольку оно накопленное. Нужны финальный `message_delta` с usage и `message_stop`; один стартовый usage недостаточен. Основание: [Anthropic streaming](https://platform.claude.com/docs/en/build-with-claude/streaming).

Это текстовый поднабор API. Инструменты, изображения, reasoning-события, structured outputs и весь OpenAI Responses API здесь не реализованы. Конкретная внешняя модель должна поддерживать выбранные поля. Результаты проверены на протокольных фикстурах и локальных HTTP-эмуляторах; совместимость с живыми аккаунтами не заявляется.

## Единица учёта

Цены — целое число внутренних кредитов за входной или выходной токен. По умолчанию primary стоит 1/3, backup — 2/4. Эти числа выбраны для демонстрации арифметики. Бюджет нового пользователя — 1 000 000 кредитов. Он накопительный: автоматического месячного сброса нет.

Оценка входа: число UTF-8 байтов сообщений плюс запас 64 на сообщение и 64 на запрос. Резерв попытки = оценка входа × input_price + max_tokens × output_price. До HTTP резервируется сумма для обеих попыток. Это приближение, а не точный tokenizer и не доказанная граница расходов.

| Что известно | Как записывается расход |
|---|---|
| Получен полный usage | Фактические токены × цены, сохранённые в попытке |
| Явный HTTP 4xx | 0, `accounting: rejected` |
| Таймаут, 5xx, оборванный поток, пропавший процесс | Весь резерв начатой попытки, `accounting: conservative_reserve` |
| Провайдер не вызывался | 0 |

Если фактический usage превышает оценку, записывается полный известный расход. `spent` может превысить бюджет, доступный остаток станет отрицательным, новые запросы не будут допущены. Шлюз ограничивает допуск по оценке; для жёсткого финансового лимита нужны ограничения на стороне провайдера и сверка его биллинга. Для cached input здесь применяется одна цена; отдельные тарифы кеширования и reconciliation не реализованы.

Каждая попытка хранит `price_version`, `input_price`, `output_price`. Смена конфигурации не меняет уже записанный расход. Цена должна быть целым числом 0–10000; для дробной денежной цены сначала выбирают подходящую единицу внутренних кредитов.

## Подключение своих двух провайдеров

Создать локальный файл `providers.env` с одной строкой `PROVIDERS=<JSON-массив из двух объектов>`. Он исключён из Git и Docker context. Формат объекта:

```json
{
  "name": "primary",
  "protocol": "openai",
  "base_url": "https://api.openai.com",
  "model": "имя-доступной-вам-модели",
  "api_key": "ваш-ключ",
  "input_price": 1,
  "output_price": 3,
  "price_version": "ваша-версия-тарифа"
}
```

Второй объект имеет другое имя, `protocol: "anthropic"`, `base_url: "https://api.anthropic.com"` и свои модель, ключ и цены. У `base_url` не должно быть суффикса `/v1`: адаптер добавляет путь сам. Имена определяют порядок primary → backup; список должен содержать ровно два разных имени. Для внешнего API использовать HTTPS. Числа в примере остаются условными, их нужно заменить собственными правилами учёта.

```bash
docker compose -f docker-compose.yml -f compose.providers.yml up --build -d --wait --wait-timeout 180
```

Smoke и recovery рассчитаны на исходные локальные эмуляторы. Не запускать их с конфигурацией реальных провайдеров: запросы будут отправлены в указанные API. Для возвращения к demo использовать обычный `docker compose up -d --force-recreate api`, без файла override.
