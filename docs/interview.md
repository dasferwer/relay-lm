# Как объяснить проект на интервью

Я сделал шлюз с одним форматом сообщений для двух LLM API. Самая важная часть — согласовать потоковый ответ, отмену и бюджет. Перед вызовом резервируется оценка обеих попыток, каждая попытка записывается отдельно. После завершения известен либо usage провайдера, либо только консервативная оценка, и в истории видно, какой способ использован.

Резервный провайдер вызывается только до первого выданного текста. После этого переключение смешало бы ответы двух моделей. При обрыве клиент получает SSE error и не должен считать уже полученный фрагмент полным ответом.

Обычная отмена закрывает upstream и освобождает резерв в защищённом cleanup. SIGKILL не даёт выполнить cleanup, поэтому незавершённую запись позже закрывает reaper по lease. Запрос с тем же ключом не вызывает генерацию заново.

В демонстрации два настоящих HTTP-сервиса эмулируют форматы провайдеров и их ошибки. Платные API не проверялись. Учёт в условных кредитах и оценка токенов не заменяют биллинг провайдера. Для реального использования я бы добавил его сверку, модельные tokenizer-ограничения, retention истории и отдельные метрики очередей и провайдеров.

На показе: `make smoke`, затем `make recovery`; в истории открыть попытки с `provider_usage` и `conservative_reserve` и объяснить различие.
